# 09｜会員機能（ログイン・マイページ）の設計

作成日：2026-09-29（同日、調査結果を反映）。ユーザーの決定（ジョブモアと同様のログインとマイページ）にもとづく設計です。仕様（01 §8・03 §3・03 §9）では求職者アカウントを初期に作らない方針だったため、変更として docs/DECISIONS_LOG.md に記録しています。M0 では画面と流れだけをデモで実装し（外部サービスに接続しない）、本実装は M1 で行います。法令の記述は判断材料で、法的な結論ではありません（法務確認が必要）。価格は USD・税別で確認日時点の値です。

## 1. ジョブモアから取り入れるもの・取り入れないもの

ジョブモア（ジョブモア株式会社、2025年10月開始）は、特定募集情報等提供事業の届出に加えて有料職業紹介事業の許可を持ち、会員向けにワンタップ応募・プロフィール（職歴・履歴書・資格）・企業とのメッセージ・スカウトを提供しています（公開のプレスリリース・アプリの説明で確認。サイトの本文は取得できず、回避していない）。

| 取り入れる | 取り入れない（理由） |
|---|---|
| ログインと登録を1画面にする、複数のログイン方法、保存（ブックマーク）、保存した検索条件と新着求人の通知、退会 | 応募の受付・応募履歴、Web履歴書・職歴・資格・生年月日・住所・電話、企業とのメッセージ・スカウト、職歴からの年収予測などの個人向けの書き添え（職業紹介にあたる・集めてはいけない情報を含むおそれ。求人マップは応募を受けない） |

## 2. 画面と流れ（M0 のデモで実装済み）

| 画面 | URL | 内容 |
|---|---|---|
| ログイン・会員登録 | `/login?next=戻り先` | 登録済みならログイン、未登録ならそのまま登録（1画面）。Google・Yahoo! JAPAN ID・LINE・Apple・メールアドレス（6桁の確認コード）。規約への同意の文をボタンの前に表示。「ログイン状態を保持する」（初期値オン）。メール配信の同意は別のチェックボックス（初期値オフ、送信者名を明記）。「ログインでお困りの方」 |
| ログインのヘルプ | `/login/help` | ログイン方法、ログインできないとき、Apple・LINE でメールアドレスを共有しない場合、退会、問い合わせ |
| マイページ | `/mypage` | 保存した求人、保存した検索条件（新着メールのオン・オフ）、最近見た求人（初期値は記録しない・削除できる）、メール配信の設定、ログイン方法、退会 |
| 検索結果 | `/jobs` | 「この条件を保存」。ログインしていなければログイン画面へ（戻り先は検索結果） |

- 保存・比較はログインしなくても使えます（このブラウザに保存）。ログインを必須にしません。
- 閲覧履歴は、会員が「閲覧履歴を残す」をオンにした場合に、ログイン中だけ記録します。表示順やおすすめには使いません（使う場合は「表示順の主な要素」として公開が必要）。
- 戻り先はサイト内の相対パスだけを受け付けます（オープンリダイレクト対策）。
- デモのログインは署名付きの Cookie（HttpOnly・SameSite=Lax）で、`APP_ENV=production` または `DATA_MODE=live` では使えません。
- M1 で追加：ログイン中の端末の一覧とログアウト、メールアドレスの追加・変更（確認コード）、連携の追加・解除（最後の1つは解除できない）、Apple の転送用アドレスの表示。

## 3. 認証の方式（推奨）

**Better Auth 1.7 系（バージョンを固定）＋ PostgreSQL（Supabase 東京）に `pg` で接続**

| 候補 | 評価 |
|---|---|
| Better Auth | Google・Apple・LINE が組込み、Yahoo! JAPAN は Generic OAuth（discovery・PKCE・発行者の検証）。メールの確認コード（未登録なら自動登録＝1画面で登録とログイン）。DB のセッション（端末一覧・失効）。Next.js 16 の `proxy.ts` に対応 |
| Auth.js（NextAuth） | 2025年9月から Better Auth のチームが保守（修正のみ）。v5 はベータのまま。メールはマジックリンクのみ |
| Supabase Auth | LINE・Yahoo! JAPAN はカスタム OIDC で追加。同意画面に supabase.co が出る（変更は有料）。同じメールの自動結合が前提 |

設定の要点（M1）：
- 同じメールでの自動結合を止める（`disableImplicitLinking: true`）。連携はログイン中の操作だけ。前回のログイン方法を案内する。
- メールの確認コード：有効期限10分程度、5回まで、ハッシュで保存、送信回数の制限と CAPTCHA。マジックリンクはセキュリティ製品の事前アクセスで使い切られることがあるため使わない。
- LINE（メールを共有しない人がいる・確認済みのフラグがない）と、審査前の Yahoo! JAPAN はメールが取れないことがあるため、仮のアドレスを入れて「未確認」とし、マイページでメールを登録するまでメールを送らない。
- 各社のアクセストークン・リフレッシュトークンは暗号化して保存する（既定では暗号化されない）。
- 「ログイン状態を保持する」は確認コード・ソーシャルログインに標準の機能がないため独自に実装する（保持しない場合は期限のない Cookie＋サーバー側を短く、保持する場合は延長ありで絶対的な上限を設ける）。
- セッションの ID は既定では DB に平文で保存される。ハッシュ化するかは M1 で判断する（DECISIONS_LOG に記録）。IP アドレスの記録は止めるか保存期間を決める。
- OAuth は PKCE・state・nonce に加え、ログイン方法が複数あるため発行者（iss）の検証で「混同攻撃」を防ぐ。Apple は `form_post` でサイトをまたいで戻るため、戻り先の設定に注意する。
- 退会では各社のトークンを失効させる（Apple は失効させないと再登録時に名前の共有画面が出ない）。

## 4. データ（M1 で DB に置く案）

| テーブル | 主な項目 | メモ |
|---|---|---|
| members | id、表示名、メールアドレス（確認済みかどうか）、作成日時、退会日時 | 退会で個人情報を消す |
| member_identities | member_id、provider、各社の利用者ID（sub）、暗号化したトークン、連携日時 | provider と sub の組で一意 |
| sessions | トークン、member_id、保持するかどうか、期限、最終利用日時、端末の概要 | ログアウト・退会で失効 |
| saved_jobs | member_id、job_id、保存日時 | ログイン時にこの端末の保存と合わせる |
| saved_searches | member_id、正規形の検索条件、保存日時、新着メールのオン・オフ、最後に通知した日時 | 20件まで |
| view_history | member_id、job_id、閲覧日時 | オンにした会員だけ。50件まで・一定期間で削除 |
| mail_preferences | member_id、新着・おすすめ・お知らせのオン・オフ、配信停止の日時 | ワンクリックの配信停止にも対応 |
| consents | member_id、同意の種類（利用規約・情報の取扱い・メール配信）、文書の版、日時、画面 | 同意の記録。メール配信は、配信をやめてから1か月以上保存 |

## 5. 法令・規約で必要になること

- 職業安定法：会員のメールアドレス・閲覧履歴・保存した条件などを集めて求人情報の提供に使うため、特定募集情報等提供事業にあたると考えられます（届出は出願中。受理の前に会員機能を公開しないのが安全）。
  - 個人情報：利用目的を具体的に示す（例：「求人情報に関するメールを配信するため」）。規約を示したうえでのボタンのクリックで同意を取る（利用を始めただけでは同意にならない）。人種・本籍・思想・労働組合への加入などを集めない。個人情報適正管理規程を作る。
  - 求職者から料金を受け取らない。登録の対価としてギフト券・ポイントを渡さない（2025年4月から原則禁止）。
  - 事業概況報告（毎年8月31日まで）、変更届（30日以内）。
  - 職業紹介との区分：全件を検索できるうえでメールで一部の求人を送るのは可。登録した職歴で選んだ求人だけを見せる・スカウトは職業紹介にあたる。
- 特定電子メール法：新着求人・おすすめ求人のメールは広告宣伝メールとして扱う。
  - 同意：送られるメールと送信者が分かる説明と、賛成の意思表示。チェックボックスの初期値はオフが推奨（オンにする場合は目立たせ、確認の表示も行う）。規約の中に埋めない。
  - 各メールに送信者の正式名称（株式会社プロセント）、住所、配信停止の方法、問い合わせ先を表示。配信停止の後は送らない。
  - 同意の記録を保存する（取得の時期・方法・画面）。
  - Gmail などの送信者要件：SPF・DKIM・DMARC、ワンクリックの配信停止（List-Unsubscribe-Post）。
- 個人情報保護法：利用目的の公表、各社から受け取る ID・メール・名前は会員の個人データとして扱う、委託先（認証・メール送信・ホスティング）と外国の事業者の扱い、開示等の請求への対応。2026年7月公布の改正（16歳未満の扱い、不適正な利用の禁止の拡大など）にも備える。
- 利用規約・情報の取扱い：会員条項（登録・連携・アカウントの管理・退会・メール配信）と、取得する情報・利用目的・保存期間を公開前に追記する（運営会社のプライバシーポリシーの更新と合わせる）。

## 6. 各社の登録・審査・費用

| ログイン方法 | 費用 | 登録・審査 | ボタンの決まり |
|---|---|---|---|
| メールアドレス（確認コード） | メール送信の費用（例：Amazon SES） | 送信ドメインの SPF・DKIM・DMARC | — |
| Google | 無料 | openid・email・profile だけなら審査は不要。同意画面にアプリ名・ロゴを出すにはブランド確認（Search Console でのドメイン確認・ホームページ・プライバシーポリシー、数分〜2〜3営業日） | 「Googleで続ける」可。白地・枠線（#747775）・標準色の G ロゴ。他のボタンと同じ程度以上に目立たせる |
| Yahoo! JAPAN ID | 無料 | アプリの登録と運営者情報の提出（発行は LINEヤフーが判断）。メールなどを取る属性取得 API は法人の利用申請と項目ごとの承認が必要。1年使わないと停止されることがある | 提供画像を改変しない。推奨は赤（#ff0033）だが必須ではなく、白地に赤いアイコンで「Yahoo! JAPAN IDで続ける」は許容範囲と読める。サイト名・ロゴより目立たせない |
| LINE | 無料 | LINE Developers でプロバイダーとチャネルを作成（チャネル名に「LINE」は使えない、プライバシーポリシーの URL が必要）。「開発中」から「公開」に切り替える。メールアドレスの取得は申請（利用者に見せる説明の画面のスクリーンショットを提出）。利用者は提供を拒否できる | **必ず緑（#06C755）と白の文字・ロゴ**（白地・枠線にそろえるのは不可）。文言は「LINEでログイン」推奨、改行しなければ独自の文言も可 |
| Apple | Apple Developer Program 年99米ドル | 法人登録に D-U-N-S 番号・法人格・組織のドメインのサイトが必要。App ID・Services ID・戻り先の登録（ファイルでのドメイン確認は不要）。非公開の転送メールを使う人のため、送信ドメインを登録（SPF か DKIM）。サーバー間の通知（メールの停止・同意の取り消し・アカウント削除）を受ける。クライアントシークレットは6か月ごとに更新 | 「Appleで続ける」は可。白・白（輪郭線）・黒。他のボタンより小さくしない |

画面：すべてのボタンを同じ大きさにし、同意の文はボタンの前に置く。Google・Apple・Yahoo! JAPAN・メールは白地・枠線でそろえ、LINE だけ緑にする。なお LINE の指定色（緑に白い文字）は WCAG のコントラストの基準を満たさないため、ボタンには公式の画像素材と代替テキストを使う。

公開の順番（推奨）：
1. メール（確認コード）と Google：審査がほぼ不要。
2. LINE：メール取得の申請と公開の切り替え。メールが取れない人の導線を先に用意する。
3. Yahoo! JAPAN ID：属性取得 API の審査に時間がかかるため、**申請は1と同時に始める**。
4. Apple：年会費・D-U-N-S・転送メールの設定が必要。Web では必須ではないため最後。

## 7. M1 の進め方

1. DB（Supabase 東京）のテーブルとマイグレーション、Better Auth の導入（メールの確認コードと Google から）。
2. 保存した求人の同期（ログイン時にこの端末の保存と合わせる）、保存した検索条件・閲覧履歴・メール配信の設定・同意の記録をサーバーに保存。
3. 新着求人メール（保存した条件ごと）と配信停止、送信ドメインの認証。
4. LINE・Yahoo! JAPAN ID・Apple を、各社の審査が済みしだい追加。
5. 退会（会員情報の削除、各社のトークンの失効）、ログイン中の端末の管理。
6. e2e：M0 のデモのテストを本実装の流れに置き換える（外部の認証はモック）。

## 8. 決めておくこと

- メール配信の同意の初期値（推奨：オフ。デモはオフ）。
- 閲覧履歴を使うか（デモは初期値オフの任意機能。使う場合も表示順には使わない）。
- セッション ID をハッシュで保存するか（Better Auth の既定は平文）。
- LINE の通知（Messaging API・公式アカウント）を使うか（料金は未確認）。
