# 09｜会員機能（ログイン・マイページ）の設計

作成日：2026-09-29。ユーザーの決定（ジョブモアと同様のログインとマイページ）にもとづく設計です。仕様（01 §8・03 §3・03 §9）では求職者アカウントを初期に作らない方針だったため、変更として docs/DECISIONS_LOG.md に記録しています。M0 では画面と流れだけをデモで実装し（外部サービスに接続しない）、本実装は M1 で行います。法令の記述は判断材料で、法的な結論ではありません（法務確認が必要）。

## 1. 画面と流れ（M0 のデモで実装済み）

| 画面 | URL | 内容 |
|---|---|---|
| ログイン・会員登録 | `/login?next=戻り先` | 登録済みならログイン、未登録ならそのまま登録（1画面）。Google・Yahoo! JAPAN ID・LINE・Apple・メールアドレス。「ログイン状態を保持する」（初期値オン）、「新着求人・おすすめ求人のメールを受け取る」（初期値オン）、利用規約・情報の取扱いへの同意の表示、「ログインでお困りの方」 |
| ログインのヘルプ | `/login/help` | ログイン方法、ログインできないとき、Apple・LINE でメールアドレスを共有しない場合、退会、問い合わせ |
| マイページ | `/mypage` | 保存した求人、保存した検索条件（新着メールのオン・オフ）、最近見た求人（削除・記録の停止）、メール配信の設定、ログイン方法、退会 |
| 検索結果 | `/jobs` | 「この条件を保存」。ログインしていなければログイン画面へ（戻り先は検索結果） |

- 保存・比較はログインしなくても使えます（従来どおり、このブラウザに保存）。ログインを必須にしません。
- 閲覧履歴は、ログイン中で「閲覧履歴を残す」がオンのときだけ記録します。
- 戻り先はサイト内の相対パスだけを受け付けます（API・外部遷移・管理画面・ログイン画面は除外。オープンリダイレクト対策）。
- デモのログインは署名付きの Cookie（HttpOnly・SameSite=Lax）で、`APP_ENV=production` または `DATA_MODE=live` では使えません。

## 2. データ（M1 で DB に置く案）

| テーブル | 主な項目 | メモ |
|---|---|---|
| members | id、表示名、メールアドレス（確認済みかどうか）、作成日時、退会日時 | 会員の本体。退会で個人情報を消し、ID だけを一定期間残す（不正の再登録対策） |
| member_identities | member_id、provider（google／yahoo_japan／line／apple／email）、provider の利用者ID（sub）、連携日時 | provider と sub の組で一意。メールアドレスだけで別の方法を自動的に同じ会員にしない |
| sessions | id（ハッシュで保存）、member_id、保持するかどうか、期限、最終利用日時、端末の概要 | ログアウト・退会で失効。パスワードの変更がないため、定期的な再認証で上限を設ける |
| saved_jobs | member_id、job_id、保存日時 | ログインしたとき、この端末の保存（localStorage）と合わせる |
| saved_searches | member_id、正規形の検索条件、保存日時、新着メールのオン・オフ、最後に通知した日時 | 20件まで |
| view_history | member_id、job_id、閲覧日時 | 50件まで・一定期間で削除。記録の停止に対応 |
| mail_preferences | member_id、新着・おすすめ・お知らせのオン・オフ、配信停止の日時 | 配信停止のリンクからも変更できる |
| consents | member_id、同意の種類（利用規約・情報の取扱い・メール配信）、文書の版、日時、画面 | 同意の記録（いつ・どの版に・どの画面で） |

## 3. セキュリティの方針

- OAuth/OIDC は認可コードフロー＋PKCE、`state` と `nonce` を検証。ID トークンの署名・発行者・宛先・期限を検証します。
- セッション Cookie は HttpOnly・Secure・SameSite=Lax。ログインの前後でセッション ID を作り直します。
- メールアドレスでのログインは、1回だけ使える短い有効期限（例：15分）のリンクか確認コード。送信回数に上限を設けます（同じアドレス・同じ接続元）。
- 別の方法での連携の追加は、ログイン中の会員が自分で行う操作だけにします（メールアドレスが同じでも自動で連携しない）。
- 会員の操作（保存・設定・退会）は同一オリジンの確認（CSRF 対策）を行います。管理画面の認証とは分けます。
- 求人本文などの取得データと会員データは別の権限で扱い、会員データを検索インデックスや外部の解析に送りません。

## 4. 法令・規約で必要になること（要点）

- 職業安定法：会員の情報（メールアドレス・閲覧履歴・保存した条件など）を集めて求人情報の提供に使うため、特定募集情報等提供事業にあたります（届出は出願中）。届出後は、個人情報の適正な管理（利用目的の明示、本人の同意、差別につながる情報を集めない、管理規程）、苦情処理、求職者から料金を受け取らないこと、毎年の事業概況報告などが必要です。
- おすすめ求人の扱い：全件を検索できるうえで一部をおすすめするのは職業紹介にあたらないと整理されています（事業者が選んだ求人だけを提供する形にしない）。
- 特定電子メール法：おすすめ求人などの広告にあたるメールは、事前の同意（登録画面のチェックボックス）と同意の記録、送信者の名称・連絡先・配信停止の方法の表示が必要です。
- 個人情報保護法：利用目的の公表、委託先（認証・メール送信・ホスティング）の監督と外国の事業者の扱い、開示等の請求への対応。
- 利用規約・情報の取扱い：会員条項（登録・連携・アカウントの管理・退会・メール配信）と、取得する情報・利用目的・保存期間を公開前に追記します（運営会社のプライバシーポリシーの更新と合わせる）。

## 6. M1 の進め方

1. DB（PostgreSQL）のテーブルとマイグレーション、認証ライブラリの導入（Google とメールから）。
2. Yahoo! JAPAN ID・LINE・Apple を追加（各社の登録と審査が済みしだい）。
3. 保存した求人の同期（ログイン時にこの端末の保存と合わせる）、保存した検索条件・閲覧履歴のサーバー保存。
4. 新着求人メール（保存した条件ごと）とメール配信の停止、送信ドメインの認証（SPF・DKIM・DMARC）。
5. 退会（会員情報の削除と、各社の連携の解除）。
6. e2e：M0 のデモのテストを本実装の流れに置き換え（外部の認証はテスト用のモックで）。
