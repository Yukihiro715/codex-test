# 08｜実ソースの審査記録（運用と現状）

確認日：2026-09-29。02 §5 の SourceReview を、1ソース＝1ファイルの審査記録として運用する方法と、現在の候補の状況・推奨です。ここでの推奨は事業上のリスク管理のための判断材料で、法的な結論ではありません。

## 1. しくみ

- 審査記録は `config/source_reviews/<sourceId>.json` に置きます（記入例は `_example.employer_public.json`）。
- 記録の形式と整合性は `packages/domain/src/source-review.ts`（`sourceReviewSchema`）で検査します。
  - 承認・サンプル取得には、判断日時・再審査期限・実ホストとパス・規約の確認日時（規約がないことの確認を含む）・自社UAでの robots の「許可」・責任者以外の確認者が必要です。
  - 未解決の blocker が残っている、自動取得を禁止している、除外レーン、範囲確認レーン（C）で法務確認が済んでいない場合は承認できません。
  - 再審査期限の最長：A（OPEN_REUSE）365日、B（PUBLIC_FACT_INDEX）180日、C（DISPUTED_SCOPE）90日。
  - 取得の上限は自社の上限（1ホスト100リクエスト/日・並列1・間隔10秒以上）を超えられません。
- ソース設定（`config/source_registry.example.json`、M1 以降は DB）は、常に審査記録の範囲内でなければなりません（`reviewPolicyViolations`）。表示方式・表示項目・ホスト・パス・保存方式・取得上限・鮮度・画像・index・JobPosting・広告利用のどれかが審査を超えると、`packages/data` の単体テストが失敗します。
- 記録があるだけでは何も有効になりません。公開・収集を有効にできるのは、期限内の承認があり、設定が審査の範囲内で、`ENABLE_LIVE_CRAWL=true` で、運営者が管理画面で操作した場合だけです（REL02）。
- robots の許可、JSON-LD、API の公開、AI による要約は、再掲載の許諾とはみなしません。不明な robots は許可として扱いません（404 で robots.txt が存在しないことを確認した場合は、RFC 9309 に従い制限なしとして記録します）。

## 2. 審査の流れ（推奨）

1. 起案（データ担当）：候補をソース設定に OFF で追加し、規約・robots・対象パス・取得/表示する項目・問題点を記録します（`decision: "pending"`）。規約・robots の本文と画面を社内の保存先に残し、sha256 を記録します。
2. 確認（責任者以外の1名以上）：`reviewers` に記名します。
3. 法務確認：C レーンと、`legal.required` を true にしたもの。
4. 判断（責任者）：`decision`（approved／sample_only／rejected）、`decidedAt`、`expiresAt` を記録します。起案者の推奨は `proposal` に分けて書き、結論と混ぜません。
5. 設定：ソース設定の `reviewId`・`reviewStatus`・`reviewExpiresAt`・`version` を審査記録に合わせます。変更は PR で2名が確認します（Git の履歴を監査記録にする）。
6. 有効化：管理画面から運営者が ON にします。`sample_only`（非公開で数十件の取得・抽出精度の確認）→ `facts_link`（小さな範囲）→ 範囲の拡大、の順に進めます。
7. 再審査：期限が来たとき、規約・robots のハッシュが変わったとき、停止・削除の依頼や苦情があったとき、401/403/CAPTCHA を検知したとき（そのソースは自動停止）。権限を自動で広げることはしません。

## 3. 記録の項目

| 項目 | 内容 |
|---|---|
| `scope` | 実ホスト、パス（前方一致）、企業、取得方法（HTML／公式API／契約フィード）、求人URLの見つけ方 |
| `terms` | 規約のURL・確認日時・本文のハッシュ、本サービスへの適用、自動取得の扱い、再利用の扱い、条件、メモ |
| `robots` | robots.txt のURL・取得日時・HTTPステータス・自社UAトークン（`KyujinMapBot`）での判定、該当したルール |
| `basis` | 利用の根拠（なぜこの範囲なら取得・表示してよいと判断したか） |
| `issues` | 問題点（blocker／major／minor、open／resolved／accepted、対応） |
| `fields` | 取得してよい項目と、表示してよい項目（表示 ⊆ 取得） |
| `storage` | 原文の保持方針と保持時間（最大72時間） |
| `displayMode` | 認める表示方式の上限（none／link_only／facts_link／full_authorized） |
| `image` `seo` `promotion` | 画像、index・JobPosting、広告（PR枠）での利用の可否と根拠 |
| `outbound` | 外部送客先のホストと応募導線の種類 |
| `crawl` `freshness` | 取得の上限、再確認の周期、確認できない求人を検索から外すまでの時間 |
| `owner` `reviewers` `legal` | 責任者、確認者、法務確認の要否と結果 |
| `proposal` `decision` `decidedAt` `expiresAt` | 起案者の推奨、結論、判断日時、再審査期限（JSTの日付の終わりまで） |
| `evidence` `notes` | 証跡（保存先・取得日時・ハッシュ）とメモ |

### 立ち上げの推奨順序
1. 企業の公式採用ページ（B）。物流・製造・介護・看護などから1〜2地域に絞る。
2. ATS 上の求人ページ（ATS ごとの規約確認のあと）。
3. ハローワーク（電話番号の方針を決めた場合だけ。小さな範囲で、鮮度を厳しく）。
4. 提携フィード（ATS・求人媒体・Indeed PLUS 連携など。利用実績ができてから）。

## 5. 求人マップ全体で守ること（職業安定法・Google）

- 求人マップは、収集した募集情報を提供する募集情報等提供事業（職業安定法4条6項2号）にあたります。
  - 的確表示（5条の4）：情報の時点（求人ごとの「情報確認」、実装済み）と、収集・更新の頻度（/sources に記載）を明らかにする。訂正・掲載中止の依頼には遅滞なく対応する。
  - 苦情処理（43条の7）：窓口を明確にする（申請・お問い合わせフォーム。電話は例示で、必須ではない）。
  - 情報提供の努力義務（43条の6）：的確表示・苦情処理・個人情報の管理・表示順の主な要素（広告費の支払いの有無を含む）を公開する（/sources・/privacy に記載）。
  - 職業紹介との区別：事業者（アルゴリズムを含む）が選んだ求人だけを提供すると職業紹介にあたる。全件を検索できるうえで一部をおすすめするのは該当しない。
  - 2025年4月の改正：求職者へのお祝い金・ポイントなどの提供は原則禁止。広告主（募集主）には、料金・違約金・解除方法を書面やメールで事前に明示する（M3 の広告契約で対応）。
- 特定募集情報等提供（届出が必要）：求職者の情報を集めて提供に使う場合。検索語の入力や絞り込みは「収集」にあたらず、現在の機能（会員登録なし・保存は端末内・個人別の並び替えなし・申請の連絡先は返信だけに使う）は該当しない可能性が高いと読めます。届出（出願中）の後は、毎年8月31日までの事業概況報告と、変更の届出が必要です。受理番号の自社サイトへの表示義務は、業務運営要領・Q&A の範囲では見当たりません。会員登録・閲覧履歴にもとづく並び替え・位置情報を使う機能を追加する前に、あらためて確認します。
- Google の JobPosting：雇用主の承認がある求人だけに付けます（許可のない代理掲載は違反例）。給与（baseSalary）は雇用主が提供した値だけ、タイトルは改変しない、一覧ページには付けない、終了した求人はすぐに外す。現在の実装（SEO02）はこの条件に合わせています。
