# 02｜提携前から始めるデータ収集戦略

## 1. 方針：提携待ちをしない。ただし「取得」と「表示」は別に設計する
「一般公開され、個別許諾を受けていない求人の条件を検索・比較できるようにする」方式を、初期の主な検証対象に含める。すべてを提携後に後回しにする方針ではない。

他方、公開情報の収集・保存・加工・表示・再配布・広告化は別の行為である。以下の管理はリスクを限定するための事業上の設計であり、合法性の認定ではない。無許諾の全文転載、写真の複製、AIでの言い換えによる原稿の置き換えは、事実条件の検索インデックスと同一視しない。[S03]

**優先順位は「企業公式の公開採用ページを分散取得」→「明示条件のある公開求人」→「ATS/媒体の公開パスを範囲別に評価」。** 一社の大規模求人媒体を丸ごと取り込むことを事業成立の前提にしない。

## 2. 4つのレーン
| レーン | 対象 | 初期の表示 | 実行条件 |
|---|---|---|---|
| A OPEN_REUSE | 転載・二次利用の条件が明示され、その条件を満たせる公開求人 | 許された範囲の求人詳細。画像は独立判定 | パス/規約/robots/更新能力を確認し有効化 |
| B PUBLIC_FACT_INDEX | 一般公開の企業採用ページ等。一般的な再掲載許諾はないが、明確な取得禁止やアクセス障壁を確認していない | 会社名、勤務地、給与単位、雇用形態、資格など必要な事実条件＋元URL | 企業・パス単位の短い内部審査。提携契約を必須にしない |
| C DISPUTED_SCOPE | ATSや媒体など、規約の適用範囲・権利・収集条件に論点がある | 初期は非公開。検討結果次第で限定facts_linkへ移す | 未解決論点・事業責任者の判断・適用範囲の根拠を記録。必要な個別法律確認を行う |
| D EXCLUDED | 非公開、認証回避が必要、対象の自動取得が明確に拒否、削除要請後、重大な権利/個人情報問題 | なし | 取得・公開を停止。別アダプターで迂回しない |

BとCは同じではない。Bを常に提携待ちにせず、Cを勝手にBへ落とさない。新規ソースの判定は1枚のSourceReviewで完結させ、法律相談の結果を待つソースがあっても、他のソースとUI実装は進める。

robotsの許可はアクセス権や転載許諾そのものではない。[S04] 明示的な制限を尊重するのは本サービスの運用方針であり、robotsだけで違法/合法を判定する趣旨ではない。

## 3. 2026-09-29時点の候補と実際の確認状況
| 候補 | 確認できた事項 | 本パッケージでの扱い |
|---|---|---|
| ハローワーク公開求人 | 一般公開求人の条件付き転載をサイトポリシーに記載。画像・地図・限定公開情報を除外、出典・運営者表示、更新・削除等が必要。[S01] | A候補。公開ポリシーを確認済み。ただしrobotsと実際の自動取得パスは未確認なのでライブは初期OFF |
| 企業独自ドメインの採用ページ | 特定企業の一覧・取得可否は今回検証していない | Bの最優先探索対象。公開パスごとに確認。50社などの数値は運用上の仮目標で、取得済み件数ではない |
| エンゲージ en-gage.net | 企業用規約に知的財産の利用制限と自動アクセス禁止がある。規約の利用者・適用範囲、企業作成物の権利も個別記載。[S02] | C。企業用規約だけで未登録第三者の法的結論は出さない。robots・個別公開パス未確認。全面自動収集を初期ONにしない |
| HRMOS / HERP / Airワーク / Talentioの公開採用ページ | 今回は個別規約、パス、robotsを未検証 | Cの調査候補。ATSであることや公開JSONがあることを利用許諾と扱わない。企業単位の掲載範囲も確認 |
| ワークゲート / type / 女の転職type / 他社求人媒体 | 本納品で取得条件を再検証していない | 媒体原稿の大量複製を初期依存先にしない。過去回答をそのまま自動取得許可に変換しない |
| hibarai / skillbridgeという表示名 | 本納品では正式事業者と原URLが未特定 | 名前からドメインを推測しない。提供元が特定できるまでadapterを作らない |

「エンゲージなら取れる」等の保証はしていない。確認したのは公開規約であり、求人全体のサンプル取得・連続更新テストではない。

## 4. 初期の探索と取り込み手順
### 4.1 サイト発見
最初は運営者が用意した企業採用URL、企業公式の採用トップ、公開sitemap、一般に利用できる検索サービスの結果から候補を得る。検索結果ページ自体を無制限にスクレイピングする方式は実装しない。外部検索APIを使う場合は、その契約に従い、有料利用を明示的に設定する。

`domain → employer → career_root → allowed_path → source_job_url` の順でスコープを狭める。発見したリンクを再帰的に無限追跡せず、同一企業の採用URLだけを対象にする。採用ページから外部ATSへ飛ぶ場合は、同じ企業でも別のsource scopeとして審査する。

### 4.2 採用ページの技術的な優先順
1. 許されたfeedまたは公開された構造化データ。
2. HTML内のJSON-LD `JobPosting`。
3. HTMLの見出し・定義リスト・表からのルール抽出。
4. 通常のブラウザ描画が必要な公開ページをPlaywrightで描画。アクセス制限回避には使わない。

JSON-LDは項目抽出の便利な形式であり、収集・転載・画像利用の許諾ではない。公開内部APIを発見しただけで、公式の自由利用APIとして扱わない。

### 4.3 最初の小規模実験
初期の提案は、B候補30〜50企業の採用ページとA候補の小さな求人範囲。職種・地域は絞り込み用メタデータとして保持し、ソース発見は職種だけに限定しない。目標件数より、更新成功率と求人の有効性を優先する。

各sourceで最初の上限は新規100ページ/日、並列1、リクエスト間隔10秒以上を提案する。これは相手が許可したレートではなく、許可条件がより厳しい場合はそちらを優先する自社上限。初回規約・robots取得も負荷に含む。大規模ホストではドメイン全体のレートを共有し、企業別adapterを増やして実質的に上限を回避しない。

更新に必要な予算を最初に確保する。例えば200件/日しか再確認できないソースを、毎日確認する前提で2万件まで増やさない。新規取得予算は、既存求人の再確認・終了反映に必要な量を差し引いた残りとする。

## 5. SourceReview：提携ではなく、公開前の内部判断
必須項目：実ホスト、パス、企業、規約URLと確認日時、robotsの取得結果と対象UAの判定、利用根拠、問題点、取得可能なフィールド、表示可能なフィールド、原文保持方針、画像可否、外部送客先、広告化の可否、オーナー、再審査期限。

Bの内部審査は、出典元への営業や返答待ちを必須としない。ただし「責任者がOKを押した」だけで第三者の権利が消えるわけではない。具体的な利用形態に争点があれば、そのソースのみ縮小/保留し、必要に応じ専門家に確認する。

確認済みソースは、最初は `sample_only`、次に `facts_link`、条件があれば `full_authorized` と段階的に拡張する。規約変更・robots変更を検知したら、自動で権限を拡大せず再審査に戻す。

## 6. 取得後の表示方式
### facts_link：無提携公開情報の基本方式
表示する：正規化した職種名、企業名、勤務地、給与の単位と範囲、雇用形態、求人で明記された必要資格・勤務形態、取得元名・URL、最終取得確認日時、元ページへのボタン。

初期は表示しない：原稿全文、魅力訴求の長文、写真、ロゴ、個人担当者名・直通メール/電話、口コミ、AIで似せた求人紹介文。説明が必要なときは、事実フィールドから短い定型文を作り、コピーに相当する文章表現を不要に取り込まない。

事実の大量集積にもデータベースの権利や利用条件等の論点があり、原稿の言い換えや短文化だけで安全になるとは断定できない。[S03] 文字数だけの「安全上限」は設定しない。

画面の注記：`公開情報をもとに条件を整理しています。募集状況・応募条件は掲載元でご確認ください。`

### full_authorized：表示根拠がある詳細
認められた範囲で本文を表示し、出典・更新・応募方法を明確にする。画像利用と本文利用は独立に制御する。元求人の条件を改変して広告する機能は持たせない。

### link_only
URL・出典等の最小限の案内に限定する。検索体験が弱くなるため、主力在庫として数えない。リンク先情報の表示にも個別条件がある場合は従う。

## 7. クロール・再確認・停止
- 実名が分かる独自User-Agentと連絡先ページを使う。Googlebot等になりすまさない。
- robotsは本仕様では24時間以内に再確認。404/410で本当に存在しない場合と、ネットワーク障害/403/不明は区別する。不明を許可扱いしない。
- 通常ページの401/403/CAPTCHAは、そのscopeを停止して再確認。429はRetry-Afterと指数的backoffで休止。別IPで取り続けない。
- HTTP条件付き取得を利用し、原稿ハッシュが同じ場合はLLMを再実行しない。
- 404/410、明示的な募集終了、正しく確認された期限超過は非掲載。タイムアウトや解析失敗は募集終了と断定せずstaleにする。
- 仮の再確認周期：活発な求人24時間、低頻度48〜72時間。7日間確認不能なら公開検索から外す。これらは自社の仮設定であり、取得元の随時更新義務等を緩めるものではない。
- expiryの終端とタイムゾーンを定義。取得日時を公開日として偽装しない。
- 削除要請、権利申立て、ソース停止時は検索結果だけでなく詳細・キャッシュ・サイトマップ・外部送客も止める。

## 8. 保存とAI処理
原HTMLは公開しない。Bでは可能な限り取得時に必要項目へ絞り、デバッグ用原文を保持する場合はsource policyで許した最小限のみ、アクセス制限・期限付きで保存する。仮の上限は72時間。これは著作権上の免責期間ではない。

AIへ渡すのは抽出に必要な本文部分。個人の直通連絡先は除く。採用ページからのプロンプトインジェクションを非信頼データとして扱い、AI出力はJSON Schemaで検証する。証拠はsource ID、URL、ページハッシュ、抽出位置、短い原文根拠またはフィールド根拠を保存する。根拠原文の保存自体もsource policyに従う。原文を保持できない場合は出典と時刻とハッシュを記録し、確認不能になった高リスク属性を出さない。

AI学習・抽出・ユーザーへの表示は別である。「AI処理だから何でも複製できる」という説明は使わない。[S03]

## 9. 苦情・訂正・削除
公開フォームからURL単位/企業単位/source単位で依頼できる。最初の段階では大量の本人確認書類を求めない。明らかな機微情報の漏洩は即時遮断、それ以外も疑義のある対象を暫定非表示にして確認する。

社内目標：高リスク報告は即時自動非表示、通常申立ては1営業日以内に初動。ソース停止/管理者非表示の反映目標は5分以内。24時間監視体制がない状態で「24時間即時対応」を約束しない。

削除tombstoneをURL・source job IDに保存し、再取得で復活させない。データを別のソースから取得できても、同一企業全体の削除請求の範囲を無視して再掲載しない。

## 10. SEOと収益化を取得許可から分離
GoogleのJobPosting、通常検索のindex、サイト内検索、広告配信は別flagにする。JobPostingは、転載条件だけでなくGoogleの必要条件と、求人企業の承認に関するポリシーも満たす場合に限定する。[S05]

Bの個別facts_linkページは初期noindex。職種×地域の編集・比較ページは、実在在庫・独自の比較価値・情報の正確性・利用範囲を確認したものだけ段階的にindexする。大量生成した薄いページで自然流入が得られると計画しない。[S06]

ハローワーク由来の担当者連絡先を営業リスト化しない。広告営業の根拠データと求人検索の原データを分け、営業に使う連絡先も別の利用根拠で管理する。[S01]

## 11. 攻めるポイントと負わないリスク
攻める：対象職種を広く保つ、企業公式サイトを分散して探索する、公開事実の整理を自動化する、小さく運用して改善する、ソースごとに止められる構成で実験回数を増やす。

負わない：一社の無許諾全文ミラーに依存する、アクセス制限を回避する、削除要求を無視する、架空求人や条件を生成する、無契約企業に請求する。これらを除いても、B/Cには法務・評判・検索流入停止の残存リスクがあることを事業判断に織り込む。
