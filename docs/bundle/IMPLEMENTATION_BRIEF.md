# WORKLENS project instructions

## Goal
- 日本語の総合求人検索サービスを作る。職種別に検索条件と比較項目を変える。
- Mimipoとのシナジーを前提にしない。長期目標は年商100億円、初期は需要と送客の検証。
- 提携交渉をMVP実装の前提にしない。公開求人の事実情報インデックスを含む段階的な収集方式。
- 開発仮称WORKLENS。正式商標・ドメイン未確認。

## Read order
1. START_HERE.md
2. docs/01_PRODUCT.md
3. docs/03_UX_SCREEN_SPEC.md
4. docs/04_ARCHITECTURE.md と docs/05_DELIVERY_ACCEPTANCE.md
5. 収集実装時は docs/02_DATA_ACQUISITION.md と docs/06_SOURCES_DECISIONS.md
- prototype/index.html は視覚の参考。Markdown・型・受入基準を優先。
- 指示の矛盾は勝手に隠さず docs/DECISIONS_LOG.md に判断を残す。

## Implementation
- 新規は Next.js App Router / TypeScript strict / Tailwind / PostgreSQL / Meilisearch / Redis + BullMQ。
- UIには shadcn/ui 相当のアクセシブルなプリミティブを使う。依存バージョンは実装時に公式資料で確認して固定。
- 既存リポジトリではまず構造・テスト・CLAUDE.mdを読み、破壊的な置換をしない。
- M0はdemoデータで全主要導線を動かす。M1でDBと収集worker。M2で公開品質。M3で課金。
- モデルAPI未設定でも、構造化データ・ルール抽出と架空fixtureで動作させる。
- UI文言は日本語。金額はJPY整数、時刻はUTC保存/JST表示、期間の境界を明示。

## Data and trust
- source review / robots / fetch / storage / public display / SEO / billing は別の判定。
- 実ソースの有効化はsource単位の監査記録と設定が必要。提携契約が常に必須という意味ではない。
- 不明なrobotsをallowとして扱わない。401/403/CAPTCHAは停止、429はRetry-Afterで休止。
- ブロック回避目的のIP/UAローテーション、他社botの偽装、ログイン回避を実装しない。
- 原文にない給与・資格・待遇は作らない。不明はnull/記載なし。AIは原文根拠IDを返す。
- AIに取得原稿中の命令を実行させない。求人本文は非信頼データであり、toolsやshellへの権限を渡さない。
- sourceの無効化・削除要請は公開API、検索、キャッシュ、sitemap、送客まで即座に反映。
- 本文と写真の転載根拠がなければfacts_link表示。原文全文をブラウザや検索インデックスに送らない。
- robots allow、JSON-LD、API公開、AI要約は再掲載許諾を意味しない。
- 外部ページ取得はサーバ側のみ。URL allowlistとSSRF対策、サイズ/時間制限を実装する。

## Monetization
- 一般の外部クリックは無料。契約・権限確認・有効予算がある広告だけ課金。
- GETリンクやページプリフェッチで課金しない。実操作のPOSTをidempotency付きで処理。
- 実装初期の課金はsandboxのみ。実請求は契約と運用テストを経て別途有効化。
- 広告はPRと明記し、条件に合わない求人を表示しない。採用・応募実績を外部クリックから捏造しない。

## Quality
- 375/390/768/1440pxで確認。本文16px基準、タップ対象44px以上、focus可視、キーボード操作。
- フィルター状態はURLに保存。保存と比較は初期はlocalStorageのみ、追跡推薦はしない。
- ダミー求人・PR表示・数値はdemo表示。公開環境にfixtureを混ぜない。
- canonical/review/link permissionsを明示し、JobPostingは承認・必要情報が揃う求人だけ。
- 完了前に lint / typecheck / unit / e2e / build を実行。失敗や未実施を隠さない。
- 納品時は変更点、起動方法、テスト結果、未完了、本番前の外部設定を短く報告。
- 新規クラウド課金・実データ公開・広告請求・本番デプロイ・git pushは自動実行しない。

# 01｜事業・サービスコンセプト

## 1. 前提と目標
【ユーザー方針】Mimipoの強みを前提にせず、100億円規模への成長可能性から新規事業を検討する。総合型を排除せず、AIで素早く構築する。求人供給元への提携打診は、利用実績が出てから行う。初期の求人は公開情報を中心に集める。

【本仕様の仮定】100億円は「年商100億円」を指す。企業価値100億円を指す場合は、売上逆算だけを後から変更する。正式ブランドと予算は未決。

## 2. 一文コンセプト
**仕事を「職種に合った条件」で比較できる、求人の横断検索サービス。**

キャッチコピー案：**働き方の違いまで、比べて探す。**
説明文案：職種ごとに必要な条件をそろえて、公開求人を横断比較。気になる仕事は、元の掲載ページで詳しく確認できます。

サービスは求人広告の検索・比較と外部送客を基本とし、人材紹介担当者による推薦、応募の取り次ぎ、採用選定、条件交渉を初期には行わない。課金の形式だけで職業紹介との区別は決まらず、実際の機能で確認する。[S07]

## 3. 「総合」と「特化」の役割を分ける
- データ基盤：職種横断で共通。source、employer、求人、勤務地、給与、雇用形態、掲載状態を統一する。
- UI：職種ごとに比較項目を変える。ドライバーの必要免許と、エンジニアの技術スタックを同じ画面に無理に押し込まない。
- 集客投資：全職種へ均等には配分せず、実測で絞る。全国対応のデータモデルと全国全件を取得する運用は別。

M0の職種一覧は8カテゴリを用意する。高度な比較条件を先行して作るのは「ドライバー」「製造・軽作業」「看護師」「IT・エンジニア」の4カテゴリ。介護・福祉、事務、営業、飲食・販売は共通条件を使う。これは市場の勝敗ではなく、UIの汎用性を検証する仮の構成である。

## 4. 最初の利用者と解決する問題
利用者は「働き方の条件はあるが、複数サイトを読み比べる手間が大きい求職者」。具体的には、日勤か、毎日帰宅できるか、必要資格は何か、月給に固定残業代が含まれるか、といった条件を確かめたい人。

提供する価値は、求人件数の多さだけではない。
1. 条件を正確に絞れる：明記された情報だけを条件にする。不明を勝手に適合へ変えない。
2. 横に並べて比べられる：給与の単位・勤務時間・資格・掲載元・情報の鮮度を同じ順序で表示する。
3. 元の求人へ迷わず進める：直接採用、紹介会社経由、ハローワーク経由など、応募方法を区別する。
4. 同じ求人が検索結果を占拠しない：同一の募集は束ね、別ソースや応募経路を展開できる。

「AIがあなたに最適な仕事を診断」「年収アップを保証」「全求人が確認済み」など、検証できない約束は使わない。

## 5. データ戦略の位置づけ
提携前でも、条件を確認した公開情報を検索対象にする。初期の中心は、企業公式採用ページ等の事実条件のインデックスと、明示条件のある転載可能求人。公開表示はソースごとに切り替え、全サイトを全文転載へ統一しない。

エンゲージのように規約の適用範囲や二次利用が不明確な候補を、調査候補から機械的に外す必要はない。ただし、未確認を「許諾済み」に変換しない。実ソースの扱いは02のレーンに従う。取得ページ数ではなく、再確認できて比較に使える「有効な固有求人件数」を資産として測る。

## 6. 収益化の段階
### 段階1：無料検索・無料外部送客
公開求人を無料で検索対象にする。契約のない企業には請求しない。外部クリックを計測するが、応募完了や採用と呼ばない。

### 段階2：確認済み広告主のクリック課金
広告主が広告契約・掲載権限・対象求人・単価・予算に同意した場合だけ有料化する。基本の課金地点は「自社サイトから広告主の求人/採用ページに進む有効な操作」。検索一覧から自社詳細を開くクリックには課金しない。求人媒体への送客は、相手との合意前に課金を見込まない。

広告枠はPR表示。検索条件を満たす求人だけを出す。比較表の並びを広告費で見えない形に変更しない。料金・停止方法・無効クリック・予算上限の説明を契約前に示す。[S07]

### 段階3：求人供給と広告販路の拡大
職種別の実測送客、再訪、応募の計測可能範囲を提示し、媒体・採用管理サービス等との連携を検討する。第三者公開データを無条件で他社へ再販売する事業は、この仕様に含めない。

## 7. 100億円の規模から逆算する
次は市場相場ではなく単純な仮定。
- 平均請求単価200円なら、年商100億円に必要な有効課金クリックは年5,000万回、月約417万回。
- 1訪問あたり有効課金クリック0.5回なら、月約833万訪問。
- ここでいうクリックは、無料求人・無効クリック・契約なし・予算切れを含まない。

指標は `訪問あたり売上 = 総外部クリック率 × 課金対象比率 × 有効化率 × 実収単価` で分解する。MVPでは課金対象比率が0の期間がある。外部送客の増加だけから将来売上を確約しない。

## 8. MVPで作るもの／作らないもの
### M0〜M2で作る
ホーム、検索、職種ハブ、情報表示権限に応じた詳細、比較3件、端末内保存、元ページへの遷移、訂正・削除申請、ソース管理、抽出レビュー、終了求人処理、基本イベント計測。

### 初期に作らない
求職者アカウント、履歴書の収集、スカウト、応募代行、面接調整、求人推薦の個人プロファイル、全自動の営業、入札オークション、企業口コミ、適性診断、給与のAI推定、モバイルアプリ、全職種のSEO記事大量生成。

### M3に回す
実広告契約、企業本人確認、広告入稿、予算管理、請求、無効クリックの精査、広告主レポート。

## 9. 仮の実験計画
- 自社原稿/架空データでM0を完成させ、比較操作の理解を確認する。
- 取得と表示の条件を確認できた小さな実ソース群で公開前検証を行う。
- 4職種のうち実データの厚みができた2職種から、検索・比較・送客を測る。
- SEOに自動的に流入が付くと置かない。初期は利用者テストと小額の集客実験も用いる。
- 一律の「PVがいくつなら成功」は置かず、掲載終了率・条件の正確性・再訪・送客単価・広告主の再購入を組み合わせる。

## 10. ブランドと独立性
色・名称・コピーはMimipoから独立。既存求人サイトの商標、ロゴ、画面、コピーの再現を狙わない。仮称を正式名称として公開しない。

# 02｜提携前から始めるデータ収集戦略

## 1. 方針：提携待ちをしない。ただし「取得」と「表示」は別に設計する
「一般公開され、個別許諾を受けていない求人の条件を検索・比較できるようにする」方式を、初期の主な検証対象に含める。すべてを提携後に後回しにする方針ではない。

他方、公開情報の収集・保存・加工・表示・再配布・広告化は別の行為である。以下の管理はリスクを限定するための事業上の設計であり、合法性の認定ではない。無許諾の全文転載、写真の複製、AIでの言い換えによる原稿の置き換えは、事実条件の検索インデックスと同一視しない。[S03]

**優先順位は「企業公式の公開採用ページを分散取得」→「明示条件のある公開求人」→「ATS/媒体の公開パスを範囲別に評価」。** 一社の大規模求人媒体を丸ごと取り込むことを事業成立の前提にしない。

## 2. 4つのレーン
| レーン | 対象 | 初期の表示 | 実行条件 |
|---|---|---|---|
| A OPEN_REUSE | 転載・二次利用の条件が明示され、その条件を満たせる公開求人 | 許された範囲の求人詳細。画像は独立判定 | パス/規約/robots/更新能力を確認し有効化 |
| B PUBLIC_FACT_INDEX | 一般公開の企業採用ページ等。一般的な再掲載許諾はないが、明確な取得禁止やアクセス障壁を確認していない | 会社名、勤務地、給与単位、雇用形態、資格など必要な事実条件＋元URL | 企業・パス単位の短い内部審査。提携契約を必須にしない |
| C DISPUTED_SCOPE | ATSや媒体など、規約の適用範囲・権利・収集条件に論点がある | 初期は非公開。検討結果次第で限定facts_linkへ移す | 未解決論点・事業責任者の判断・適用範囲の根拠を記録。必要な個別法律確認を行う |
| D EXCLUDED | 非公開、認証回避が必要、対象の自動取得が明確に拒否、削除要請後、重大な権利/個人情報問題 | なし | 取得・公開を停止。別アダプターで迂回しない |

BとCは同じではない。Bを常に提携待ちにせず、Cを勝手にBへ落とさない。新規ソースの判定は1枚のSourceReviewで完結させ、法律相談の結果を待つソースがあっても、他のソースとUI実装は進める。

robotsの許可はアクセス権や転載許諾そのものではない。[S04] 明示的な制限を尊重するのは本サービスの運用方針であり、robotsだけで違法/合法を判定する趣旨ではない。

## 3. 2026-09-29時点の候補と実際の確認状況
| 候補 | 確認できた事項 | 本パッケージでの扱い |
|---|---|---|

## 4. 初期の探索と取り込み手順
### 4.1 サイト発見
最初は運営者が用意した企業採用URL、企業公式の採用トップ、公開sitemap、一般に利用できる検索サービスの結果から候補を得る。検索結果ページ自体を無制限にスクレイピングする方式は実装しない。外部検索APIを使う場合は、その契約に従い、有料利用を明示的に設定する。

`domain → employer → career_root → allowed_path → source_job_url` の順でスコープを狭める。発見したリンクを再帰的に無限追跡せず、同一企業の採用URLだけを対象にする。採用ページから外部ATSへ飛ぶ場合は、同じ企業でも別のsource scopeとして審査する。

### 4.2 採用ページの技術的な優先順
1. 許されたfeedまたは公開された構造化データ。
2. HTML内のJSON-LD `JobPosting`。
3. HTMLの見出し・定義リスト・表からのルール抽出。
4. 通常のブラウザ描画が必要な公開ページをPlaywrightで描画。アクセス制限回避には使わない。

JSON-LDは項目抽出の便利な形式であり、収集・転載・画像利用の許諾ではない。公開内部APIを発見しただけで、公式の自由利用APIとして扱わない。

### 4.3 最初の小規模実験
初期の提案は、B候補30〜50企業の採用ページとA候補の小さな求人範囲。職種・地域は絞り込み用メタデータとして保持し、ソース発見は職種だけに限定しない。目標件数より、更新成功率と求人の有効性を優先する。

各sourceで最初の上限は新規100ページ/日、並列1、リクエスト間隔10秒以上を提案する。これは相手が許可したレートではなく、許可条件がより厳しい場合はそちらを優先する自社上限。初回規約・robots取得も負荷に含む。大規模ホストではドメイン全体のレートを共有し、企業別adapterを増やして実質的に上限を回避しない。

更新に必要な予算を最初に確保する。例えば200件/日しか再確認できないソースを、毎日確認する前提で2万件まで増やさない。新規取得予算は、既存求人の再確認・終了反映に必要な量を差し引いた残りとする。

## 5. SourceReview：提携ではなく、公開前の内部判断
必須項目：実ホスト、パス、企業、規約URLと確認日時、robotsの取得結果と対象UAの判定、利用根拠、問題点、取得可能なフィールド、表示可能なフィールド、原文保持方針、画像可否、外部送客先、広告化の可否、オーナー、再審査期限。

Bの内部審査は、出典元への営業や返答待ちを必須としない。ただし「責任者がOKを押した」だけで第三者の権利が消えるわけではない。具体的な利用形態に争点があれば、そのソースのみ縮小/保留し、必要に応じ専門家に確認する。

確認済みソースは、最初は `sample_only`、次に `facts_link`、条件があれば `full_authorized` と段階的に拡張する。規約変更・robots変更を検知したら、自動で権限を拡大せず再審査に戻す。

## 6. 取得後の表示方式
### facts_link：無提携公開情報の基本方式
表示する：正規化した職種名、企業名、勤務地、給与の単位と範囲、雇用形態、求人で明記された必要資格・勤務形態、取得元名・URL、最終取得確認日時、元ページへのボタン。

初期は表示しない：原稿全文、魅力訴求の長文、写真、ロゴ、個人担当者名・直通メール/電話、口コミ、AIで似せた求人紹介文。説明が必要なときは、事実フィールドから短い定型文を作り、コピーに相当する文章表現を不要に取り込まない。

事実の大量集積にもデータベースの権利や利用条件等の論点があり、原稿の言い換えや短文化だけで安全になるとは断定できない。[S03] 文字数だけの「安全上限」は設定しない。

画面の注記：`公開情報をもとに条件を整理しています。募集状況・応募条件は掲載元でご確認ください。`

### full_authorized：表示根拠がある詳細
認められた範囲で本文を表示し、出典・更新・応募方法を明確にする。画像利用と本文利用は独立に制御する。元求人の条件を改変して広告する機能は持たせない。

### link_only
URL・出典等の最小限の案内に限定する。検索体験が弱くなるため、主力在庫として数えない。リンク先情報の表示にも個別条件がある場合は従う。

## 7. クロール・再確認・停止
- 実名が分かる独自User-Agentと連絡先ページを使う。Googlebot等になりすまさない。
- robotsは本仕様では24時間以内に再確認。404/410で本当に存在しない場合と、ネットワーク障害/403/不明は区別する。不明を許可扱いしない。
- 通常ページの401/403/CAPTCHAは、そのscopeを停止して再確認。429はRetry-Afterと指数的backoffで休止。別IPで取り続けない。
- HTTP条件付き取得を利用し、原稿ハッシュが同じ場合はLLMを再実行しない。
- 404/410、明示的な募集終了、正しく確認された期限超過は非掲載。タイムアウトや解析失敗は募集終了と断定せずstaleにする。
- 仮の再確認周期：活発な求人24時間、低頻度48〜72時間。7日間確認不能なら公開検索から外す。これらは自社の仮設定であり、取得元の随時更新義務等を緩めるものではない。
- expiryの終端とタイムゾーンを定義。取得日時を公開日として偽装しない。
- 削除要請、権利申立て、ソース停止時は検索結果だけでなく詳細・キャッシュ・サイトマップ・外部送客も止める。

## 8. 保存とAI処理
原HTMLは公開しない。Bでは可能な限り取得時に必要項目へ絞り、デバッグ用原文を保持する場合はsource policyで許した最小限のみ、アクセス制限・期限付きで保存する。仮の上限は72時間。これは著作権上の免責期間ではない。

AIへ渡すのは抽出に必要な本文部分。個人の直通連絡先は除く。採用ページからのプロンプトインジェクションを非信頼データとして扱い、AI出力はJSON Schemaで検証する。証拠はsource ID、URL、ページハッシュ、抽出位置、短い原文根拠またはフィールド根拠を保存する。根拠原文の保存自体もsource policyに従う。原文を保持できない場合は出典と時刻とハッシュを記録し、確認不能になった高リスク属性を出さない。

AI学習・抽出・ユーザーへの表示は別である。「AI処理だから何でも複製できる」という説明は使わない。[S03]

## 9. 苦情・訂正・削除
公開フォームからURL単位/企業単位/source単位で依頼できる。最初の段階では大量の本人確認書類を求めない。明らかな機微情報の漏洩は即時遮断、それ以外も疑義のある対象を暫定非表示にして確認する。

社内目標：高リスク報告は即時自動非表示、通常申立ては1営業日以内に初動。ソース停止/管理者非表示の反映目標は5分以内。24時間監視体制がない状態で「24時間即時対応」を約束しない。

削除tombstoneをURL・source job IDに保存し、再取得で復活させない。データを別のソースから取得できても、同一企業全体の削除請求の範囲を無視して再掲載しない。

## 10. SEOと収益化を取得許可から分離
GoogleのJobPosting、通常検索のindex、サイト内検索、広告配信は別flagにする。JobPostingは、転載条件だけでなくGoogleの必要条件と、求人企業の承認に関するポリシーも満たす場合に限定する。[S05]

Bの個別facts_linkページは初期noindex。職種×地域の編集・比較ページは、実在在庫・独自の比較価値・情報の正確性・利用範囲を確認したものだけ段階的にindexする。大量生成した薄いページで自然流入が得られると計画しない。[S06]

ハローワーク由来の担当者連絡先を営業リスト化しない。広告営業の根拠データと求人検索の原データを分け、営業に使う連絡先も別の利用根拠で管理する。[S01]

## 11. 攻めるポイントと負わないリスク
攻める：対象職種を広く保つ、企業公式サイトを分散して探索する、公開事実の整理を自動化する、小さく運用して改善する、ソースごとに止められる構成で実験回数を増やす。

負わない：一社の無許諾全文ミラーに依存する、アクセス制限を回避する、削除要求を無視する、架空求人や条件を生成する、無契約企業に請求する。これらを除いても、B/Cには法務・評判・検索流入停止の残存リスクがあることを事業判断に織り込む。

既定は条件適合→正確性→鮮度→関連度。広告とは別の自然検索順序。給与順は同一単位の確認できた下限額を使い、未記載は末尾。新着順は元の公開日があれば使用し、なければ初回検出日と明記する。

### 状態
loading：skeleton。0件：条件を個別に緩める提案。error：既存結果を保持し再試行。stale：確認日時を注意表示。条件を裏で外して件数を水増ししない。

`全国×全職種×すべての市区町村×すべての条件`の全組合せを生成しない。SEO用に公開するページは管理されたリストで別途決める。[S06]

## 7. S04 求人詳細
### facts_linkモード
タイトル、企業、給与条件、勤務地、勤務形態、職種別条件表、出典/取得日時、注記、元ページCTA、訂正/削除。
本文エリアを空白の「求人説明」にしない。「比較用の条件概要」と明示する。企業の紹介文をAIで補わない。

### full_authorizedモード
上記に加え、認められた本文の仕事内容、必須/歓迎条件、給与内訳、勤務・休暇、応募方法を表示。労働条件の意味を変える要約をしない。

PC右：幅300pxのsticky条件サマリー＋主CTA。スマホ下：安全領域を含むsticky CTA。「元の求人ページで確認」または「ハローワークで応募方法を確認」。自社で応募を受けないため、単独の「応募完了」ボタンはない。

複数掲載元がある場合は「他の掲載元」を展開。最も条件のよい給与だけを他ソースから合成しない。主表示には1つのsource listingを明示して紐づける。

給与内訳：金額範囲、単位、固定残業代の有無・時間・金額、手当の扱い。記載がないものは不明。年収換算機能は初期に作らない。

掲載終了：検索から除外、CTA無効、「この求人の掲載は終了しています」。削除依頼による非公開：原条件を再表示せず、必要な最小限の状態案内だけ。

## 8. S05 比較
最大3件。PCは項目列＋求人3列、スマホは見出し固定の横スクロールで比較。アクセシブルなtableを使い、横スクロールの存在を示す。
比較項目：職種、会社、勤務地、給与と単位、残業代、雇用形態、勤務時間、必要資格、職種固有項目、応募経路、出典、情報確認日時。
「違いだけ表示」を提供。unknown同士を有利/不利に判定しない。異職種の比較は共通項目が中心になり、適用しない欄は「対象外」。
各列に削除/保存/元ページCTA。1件以下では比較の説明と追加導線。4件目を追加すると既存を黙って消さず、上限を案内。

## 9. S06 保存
初期は端末のlocalStorageにjob IDのみ保存。個人アカウントやメールは不要。他端末には引き継がれない旨を表示。
保存した求人が消えたら、未公開本文をlocalStorageから復活させない。「掲載終了/非公開」の最小表示と削除操作を残す。保存順/情報確認順で並び替え。

## 10. S07 訂正・削除
対象URLは可能なら自動入力。申請種別：募集終了、条件違い、掲載停止希望、個人情報、その他。
連絡先は返答希望の場合に入力。本人確認書類のアップロードを初期必須にしない。自動返信は実際に送信できる場合だけ。受付番号を表示し、「削除を約束する」ではなく「対象の確認・必要な対応を行う」とする。
実装はレート制限、CSRF対策、スパム対策を行う。機微情報をメールやanalyticsへそのまま送らない。

## 11. 管理画面
A01：source名、レーン、公開件数、取得成功率、最終成功、stale件数、規約/robots確認日、ON/OFF。赤い「公開停止」をデータ削除と分ける。
A02：対象ホスト/パス、規約根拠、robots、取得上限、原文保持、表示フィールド、本文/画像/SEO/広告の権限。判定履歴と変更者を表示。
A03：原文根拠と抽出値の対比、資格/給与の矛盾、承認・修正・却下。元HTMLは隔離表示しscriptを実行しない。
A04：受付、対象求人、暫定非公開、対応履歴、再掲載防止。source単位の停止を提供。
A05：有効固有求人、期限切れ率、条件正確性、訪問、検索、比較、外部送客。外部応募未計測なら「未計測」と表示。

## 12. 広告主画面（M3）
最初に企業/代理店の権限確認、契約同意、対象求人を確認。広告一覧は日予算、総予算、CPC、配信期間、状態、使用額、即時停止。
レポートは総操作、有効クリック、除外理由、税抜利用額、消費税、請求額を分ける。応募・採用は計測根拠がある場合だけ。デフォルト価格を実相場と説明しない。

## 13. アクセシビリティとエラー
44px以上のタップ対象、可視focus、form label、aria-liveで件数更新、dialogのfocus trapとEsc、比較のtable caption。色だけでPR/注意/不明を区別しない。
375/390/768/1440pxを検証。長い社名、3行の職種、給与未記載、英数字混在をfixtureに含める。横はみ出しは比較表以外禁止。

## 14. 視覚的な完成判定
- ホームで「何を検索するサービスか」「何で探せるか」が即座に分かる。
- 検索結果の上部に余分な巨大バナーがなく、最初の求人まで近い。
- 給与の単位・応募経路・source・取得日時が読み取れる。
- 濃い影やカラフルなカードで情報の優先順位を壊さない。
- 画像がなくても成立する。実企業の写真や他社の画面を勝手に素材化しない。

# 04｜技術・データ・処理設計

## 1. 推奨構成
本項は設計提案。新規構築はNext.js App Router + TypeScript strict + Tailwind CSS、UIプリミティブはshadcn/ui相当。Node.jsは実装時の現行LTSと依存の互換性を確認して固定する。Next.js公式の現行初期設定を参照し、過去の設定を推測で流用しない。[S10]

APIはNext.jsのRoute Handlerで開始。PostgreSQLを正本とし、Meilisearchで日本語検索と絞り込みを提供。収集/抽出/索引更新はWebリクエストから切り離したNode worker、Redis + BullMQを利用。Meilisearchのfilterable/sortable設定は明示し、設定変更時はtask完了を待つ。[S11]

M0は同じRepositoryインターフェイスに対するfixture実装。M1でDB/検索/workerを差し替える。ローカルはDocker ComposeでDB/Redis/検索を起動。クラウドの契約・本番構成は本仕様で勝手に確定しない。

LLMはモデル非依存のExtractionProvider。APIキー未設定ならルール抽出のみ。モデルの名称・価格は仮で固定しない。LLMを検索の必須経路にせず、構造化データ/ルールを優先する。

## 2. 想定ディレクトリ
```
apps/web/                  # 求職者UI、公開API、管理UI
apps/worker/               # 収集、抽出、終了判定、検索投影
packages/domain/           # 型、スキーマ、policy gate、給与/資格ルール
packages/data/             # DB、repository、検索adapter
packages/ui/               # 共通UI
config/                    # 職種・source scope・design tokens
fixtures/                  # 架空の求人/HTML/失敗ケース
infra/                     # ローカルCompose
```
小規模な既存repoではモノレポ化を強制せず、同じ責務をフォルダで分けてもよい。

## 3. 正本データモデル
### Source / SourceScope / SourceReview
Sourceは運営元単位、SourceScopeはhost/path/企業単位。クロール上限はhostでも共有する。Reviewはterms URL/hash、robotsの状態、レーン、判断根拠、判断者、有効期限、利用可能フィールドを記録。

policyは `fetch_allowed`、`storage_mode`、`display_mode`、`public_enabled`、`seo_index_allowed`、`jobposting_allowed`、`image_allowed`、`commercial_promotion_allowed` を分離。公開レーンと契約状態を混同しない。

### Employer
id、表示名、正規化名、法人番号（確認できる場合のみ）、公式URL、住所の必要範囲、公式URLの確認根拠。社名だけで同一企業と断定しない。

### SourceListing（ソース上の募集1件）
source scope、source job ID、canonical URL、元の募集職種、employer、occupation、locations[]、employmentTypes[]、salary、facts、sourcePostedAt、firstSeenAt、lastFetchedAt、lastChangedAt、validThrough、state、contentHash、evidence refs。

### JobCluster（横断的な同一募集の束）
複数SourceListingを束ねる。元の求人と出典は失わない。雇用先・職種・勤務地・雇用形態・勤務条件・求人番号を照合し、初期は保守的に重複判定。紹介会社が異なる、給与が矛盾する、勤務地が異なる場合は無理に合体しない。

### FieldEvidence / ExtractionRun
field、value、元ページhash、取得日時、抽出手法、根拠位置、必要最小限の根拠、review状態。LLM confidenceは確率としてユーザーへ表示しない。原文を保持できない場合はフィールドの出典・ハッシュを残し、根拠の再確認が難しい条件は限定表示。

### CrawlRun / FetchAttempt
日時、URL、HTTP status、robots判定、取得サイズ、ETag/Last-Modified、解析状態、失敗原因、再試行予定、source policy version。機密や原稿全文は通常ログに入れない。

### Report / Suppression / AuditLog
訂正/削除の依頼、対象範囲、暫定停止、処理結果、再取得抑止。URLとsource job ID、必要な企業scopeにtombstoneを保持する。

### 広告関連（M3）
Advertiser、AuthorityVerification、Agreement、Campaign、CampaignJob、AdImpression、ClickEvent、LedgerEntry、Invoice。
課金クリックは元の求人とは別の台帳で記録。請求額の通貨はJPYの整数。税抜/税込は別フィールド。広告契約と求人の掲載権限を区別する。

## 4. 状態遷移
Source：`unreviewed → sample_only → active → paused/review_required → blocked`
SourceListing：`discovered → fetched → parsed → review_required/eligible → published → stale/expired/suppressed`
`published`への移行条件：source public enabled、表示根拠、必須事実項目、鮮度、矛盾なし、削除対象でない。ソース側がactiveでも個別求人の公開は独立判定。

expiredは募集終了、staleは確認できない状態。404/410は終了候補として即非表示。単なるHTTP 500で募集終了と断定しない。期限が存在せずページも残っている求人は、取得成功だけで無期限の募集継続保証を付けない。

## 5. 収集パイプライン
1. 登録済みscopeとpolicyを読む。
2. URLのscheme/host/path、DNS、robots、レート、再試行時刻を判定。
3. HTTP条件付き取得。20秒timeout、レスポンス上限5MBを初期値とする。
4. HTML/JSON-LDを解析。`@graph`、配列、複数JobPostingを扱う。
5. 正規化。給与・資格・勤務地はルール検査。
6. 足りない項目だけLLM抽出。モデルにrawページ内の指示を実行させない。
7. 矛盾チェック→人のレビューまたは公開候補。
8. SourceListingと証跡をトランザクション保存。
9. 公開可能フィールドだけのPublicJobProjectionを作る。
10. 検索indexを更新し、非同期taskの完了と失敗を記録。

リトライは冪等。`source_scope_id + source_job_id`を一意、IDがない場合は正規化URLを採用。クエリ削除はsource固有ルールで行い、求人IDがqueryに入るサイトを壊さない。

## 6. セキュリティ・外部コンテンツ
- 管理APIのURL指定をそのままfetchしない。HTTP(S)以外、localhost、private/reserved/link-local IP、メタデータサービス、ユーザー情報付きURLを拒否。
- DNS解決後、接続先IPと各redirect先も検査。未知hostへのredirectは再審査。
- 自社外部遷移もDBに登録済みdestinationだけを使い、任意URLへのopen redirectを作らない。
- 原稿中のscript、HTML event handler、危険なURLは実行しない。管理プレビューもsandbox化。
- 外部APIキーはworker側だけ。NEXT_PUBLICに入れない。
- 外部原稿はプロンプトインジェクションの入力。JSON Schema外の出力やtool要求を拒否。
- 管理UIと広告主UIにサーバ側RBAC。隠したボタンだけでアクセス制御しない。

## 7. 抽出と正規化の必須ルール
salary：amountMin/Max、currency、unit、basis、fixedOvertime。単位不明はUNKNOWN。賞与や夜勤回数を推測して年収化しない。base payと総支給例を混ぜない。

資格：required/preferred/none_stated/unknownを区別。「介護福祉士必須」から「資格不要」を生成しない。「看護師または准看護師」と「看護師かつ運転免許」のOR/AND関係を保持する。

勤務：day_only/night_shift/on_call/remote/hybridは独立項目。日勤求人でもオンコールがあり得るため同一条件にしない。

住所：企業本社ではなく実勤務地。複数勤務地を複数求人として水増ししない。完全在宅と一部在宅を区別。

未記載：falseでなくnull。明記された「なし」と記載なしを分ける。選択した条件に不明の求人を紛れ込ませない。

## 8. 公開API
| Method / Path | 役割 | 注意 |
|---|---|---|
| GET /api/jobs | 検索、facet、ページング | queryをZod等で検証、最大limit制限 |
| GET /api/jobs/:id | 公開projection | raw bodyや許可外フィールドを返さない |
| GET /api/compare?ids=... | 最大3件の比較 | 各求人の公開状態を再検査 |
| POST /api/reports | 訂正/削除 | レート制限、入力検査、受付ID |
| POST /api/outbound | 明示クリックを記録して遷移 | サーバ管理のdestination、idempotency |
| GET /out/:id | JSなしの無料遷移 | GETは計測補助のみ、課金しない |
| GET/POST /api/admin/sources | source管理 | 認可、監査、公開/停止の分離 |
| POST /api/admin/sources/:id/pause | 停止 | 公開拒否フラグを先に書き込む |
| POST /api/admin/review/:id | 条件訂正 | 元値と変更根拠を監査保存 |

検索は非同期indexの結果をそのまま返さず、候補job IDsの公開状態/停止フラグをDBまたは即時denylistで再チェックする。停止済み求人がキャッシュに残ってもユーザーへ漏らさない。source停止後の再index処理で復活しないようpolicy versionを照合する。

## 9. クリック課金設計（M3）
初期は固定CPC＋予算で開始し、オークションは不要。単価は契約データから取得し、clientの金額を信用しない。

手順：広告表示時にcampaign/job/policy version/expiry/nonceを署名した短命tokenを発行→ユーザーの明示操作でPOST→token、求人、契約、期間、予算、重複、不正兆候を検査→DB transactionで残予算を確保し台帳記帳→固定の登録URLへ303 redirect。

free clickの場合は請求台帳へ入れない。GET・prefetch・crawler・広告主自身のテストはbillable=false。同じidempotency keyは同一結果を返す。重複クリックの窓は契約で定義し、初期案は同じsession/job/campaignの30分以内を除外。IPだけで個人を決めつけない。

予算切れでは課金しない。求人自体を無料として掲載する場合はPR枠から外す。短時間の競合リクエストでも予算上限を超えないtransactionテストを必須にする。

serverの303送出は応募完了や相手ページ到達の保証ではない。契約上の課金地点を「有効な外部遷移操作」と定義し、到達保証型と混同しない。後日判明した不正クリックはledgerの相殺で対応し、過去記録を破壊的に書き換えない。

## 10. 計測と個人情報
初期イベント：search_submitted、filter_applied、job_viewed、saved_toggled、compare_opened、outbound_clicked、report_submitted。
属性：job ID、source ID、occupation、page、位置、PR区分、フィルターのコード。自由記述検索はPIIを含む可能性があるため標準analyticsへそのまま送らない。元URLに個人情報・トークンがある場合も除去。

保存はjob IDを端末内だけに保つ。通知、メール、個人化推薦、履歴書収集は初期OFF。機能を追加する場合は特定募集情報等提供事業の届出や個人情報の取扱いを再確認する。[S07]

Cookie規制・第三者解析ツールへのデータ送信は導入前に確認。M0は外部analyticsなし。クリックの不正防止情報は必要最小限、HMAC等を用い、raw IPの長期保有を既定にしない。保存期間を設定し、法定保管対象になる請求書等は別の保存ルールで管理。

## 11. SEO
- facts_link求人は初期noindex。サイト内検索には利用できる。
- 検索queryの組合せページは原則noindex。公開する職種/地域ハブはallowlist。
- JobPostingは1求人の詳細に限定し、承認/必要情報/表示内容/期限/応募導線を検査。baseSalaryはGoogleの雇用主向け指定条件を確認し、第三者集約の初期出力からは外す。[S05]
- canonical、公開日、lastmodを偽装しない。AIで類似説明を量産して固有ページと装わない。[S06]
- 自社サイトのrobotsは検索エンジンがnoindexを読み取れるよう設計し、robots遮断とnoindexを無計画に併用しない。

## 12. ローカル実行・CI
Claude Codeは次のscriptsを実装：`dev` `build` `lint` `typecheck` `test` `test:e2e` `db:migrate` `db:seed:demo` `worker`。実装していないコマンドを起動方法として書かない。

`.env.example`にダミー値と説明を入れ、キーは含めない。`DATA_MODE=demo`、`ENABLE_LIVE_CRAWL=false`、`ENABLE_BILLING=false`、`ENABLE_JOBPOSTING=false`が初期値。NODE_ENVだけでfixture混入防止を判定せず、本番起動時のfixture存在検査を入れる。

CIはunit/integration/e2e/build。ネットワークテストとfixtureテストを分離し、CIから勝手に外部サイトへ連続アクセスしない。

## contracts/domain.ts

```typescript
// Design contract, not a finished application. Add runtime validation in implementation.
export type RiskLane = 'OPEN_REUSE' | 'PUBLIC_FACT_INDEX' | 'DISPUTED_SCOPE' | 'EXCLUDED';
export type DisplayMode = 'none' | 'link_only' | 'facts_link' | 'full_authorized';
export type ListingState = 'discovered' | 'fetched' | 'parsed' | 'review_required' | 'eligible' | 'published' | 'stale' | 'expired' | 'suppressed';
export type SalaryUnit = 'HOUR' | 'DAY' | 'MONTH' | 'YEAR' | 'UNKNOWN';
export type TriState = 'yes' | 'no' | 'unknown';
export type ApplicationRoute = 'employer' | 'agency' | 'hellowork' | 'jobboard' | 'unknown';
export interface FieldEvidence {
  id: string; sourceListingId: string; field: string; fetchedAt: string;
  pageHash: string; method: 'jsonld' | 'rule' | 'llm' | 'human';
  locator: string | null; excerpt: string | null;
  reviewed: boolean; retentionUntil: string | null;
}
export interface SourcePolicy {
  id: string; version: number; lane: RiskLane;
  hosts: string[]; allowedPaths: string[];
  reviewStatus: 'unreviewed' | 'sample_only' | 'approved' | 'rejected';
  reviewId: string | null; reviewExpiresAt: string | null;
  fetchEnabled: boolean; publicEnabled: boolean; displayMode: DisplayMode;
  storageMode: 'none' | 'facts_only' | 'ephemeral_raw' | 'licensed_raw';
  publicFields: string[]; imageAllowed: boolean;
  seoIndexAllowed: boolean; jobPostingAllowed: boolean;
  commercialPromotionAllowed: boolean;
  maxRequestsPerHostPerDay: number; maxConcurrencyPerHost: number;
  minRequestIntervalMs: number; maxResponseBytes: number;
  rawRetentionHours: number; staleHideAfterHours: number;
}
export interface Salary {
  currency: 'JPY'; min: number | null; max: number | null;
  unit: SalaryUnit; basis: 'base' | 'gross' | 'example' | 'unknown';
  fixedOvertimeIncluded: TriState; fixedOvertimeHours: number | null;
  fixedOvertimeAmount: number | null; evidenceIds: string[];
}
export interface JobLocation {
  country: 'JP'; prefectureCode: string | null; city: string | null;
  displayAddress: string; remoteMode: 'onsite' | 'hybrid' | 'remote' | 'unknown';
}
export interface SourceListing {
  id: string; sourceScopeId: string; sourceJobId: string;
  canonicalUrl: string; employerId: string; title: string;
  occupation: string; locations: JobLocation[]; employmentTypes: string[];
  salary: Salary; facts: Record<string, string | number | string[] | null>;
  evidenceIds: string[]; state: ListingState;
  sourcePostedAt: string | null; firstSeenAt: string; lastFetchedAt: string;
  lastChangedAt: string; validThrough: string | null; contentHash: string;
  applicationRoute: ApplicationRoute; demo: boolean;
}
// The public API must use this explicit projection, never serialize SourceListing/raw HTML directly.
export interface PublicJob {
  id: string; primaryListingId: string; title: string; employerName: string;
  occupation: string; locations: JobLocation[]; employmentTypes: string[];
  salary: Salary; facts: Record<string, string | number | string[] | null>;
  displayMode: DisplayMode; sourceName: string; sourceUrl: string;
  lastFetchedAt: string; sourcePostedAt: string | null;
  applicationRoute: ApplicationRoute; state: 'published' | 'stale';
  authorizedDescription: string | null; demo: boolean;
}
export interface OutboundRequest {
  jobId: string; primaryListingId: string;
  impressionToken: string | null; idempotencyKey: string;
  placement: 'search' | 'detail' | 'compare';
}
export interface ClickDecision {
  eventId: string; billable: boolean; cpcJpy: number;
  reason: 'valid' | 'free' | 'duplicate' | 'no_contract' | 'budget_exhausted' | 'inactive' | 'bot' | 'test';
  destination: string;
}
export interface SourceAdapter {
  discover(scope: SourcePolicy): AsyncIterable<string>;
  parse(html: string, sourceUrl: string): Promise<Partial<SourceListing>[]>;
}
// Implementation must put fetch authorization, SSRF checks, robots and host throttling
// in a common fetch layer, outside individual adapters.
```
